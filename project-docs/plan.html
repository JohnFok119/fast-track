    What solves what

    Feature to pain to persona

    Hover over or focus any box to trace its chain. Solid lines are a direct fix. Dashed lines are a partial one: the clocks panel shows legal deadlines, not observed review times, and the nonprofit PM's drift pain is medium. All four personas are made up from public research.

    Who benefits in the end

    Local workers who move in sooner. They are the reason in the pitch, not users of the tool.

    Pains this does not solve (and the pitch won't claim)

    Fee totals, funding rounds, observed review times (a Stretch, from APR data), and 34 different rulebooks. The last one is the scale story: a new city is a new data file, not new code.

    Sponsor lens (new, 11:50)

    Habitat for Humanity of Orange County is the sponsor

    The Impact question is "would a nonprofit or city use it next month?" A Habitat OC style project manager is that nonprofit, so that persona moves from last to first in the pitch. The plan stays honest about what the checker fixes for them and what it doesn't.

    What our research says (public sources, not interviews)

    • They deliver 4 to 12 for-sale homes per project and want the fewest months of carrying cost.
    • Their biggest pains are timelines (10 to 42 months from approval to permit) and funding rounds.
    • City rules drifting from state law is a medium pain for them.

    Nothing about Habitat OC itself is claimed until it is sourced. In P1, the sources worker spends 10 minutes on Habitat OC's public pages and logs what it finds in FINDINGS.md.

    What it changes in the pitch

    • Lead with the nonprofit PM and the city permit tech, the two people who would use it next month.
    • The honest claim: it catches a city requirement that state law doesn't allow before submittal, instead of after a refusal. That removes one cause of delay. It does not shorten funding rounds.
    • The next step is the for-sale paths (SB 9 lot splits, SB 684 small lots): same engine, new rules.

    New guard: lawful covenants

    Affordable for-sale homes often carry lawful resale or affordability covenants. A rule that flags every "deed restriction" would tell Habitat's own staff their covenants are unlawful, which is the worst kind of confident wrong answer.

    So: the CONFLICTS rule matches only a covenant the city requires as a condition of an ADU permit, as in HCD's Irvine finding. Any other covenant is UNKNOWN. A new test asserts that an affordability covenant is not flagged CONFLICTS.

    Data flow

    From a saved checklist to a draft reply

    Everything in the solid boxes is deterministic: the same input always gives the same flags. Claude is optional (the dashed boxes). It can suggest a rule ID or reword the letter, but it never writes a citation, and its output passes an ID check before it is used.

    Why the ID check

    If the assist (or anything else) names a rule ID that isn't in the rule set, the item becomes UNKNOWN. The model can't add law.

    Why "no source, no rule"

    The rule loader refuses a rule whose source ID is missing from the sources index. Test 3 holds by construction, and a test checks it.

    Why nothing sends

    The app has no mail, form or network code. A test scans src/ for one (test 4).

    Technical choices

    What we build with, and why

    Deterministic rule engine

    Flags come only from curated rules in versioned JSON. Same input, same flags.

    Why: "a confident wrong answer is the worst outcome". Tests can assert exact flags.
    Rejected: letting a model judge conflicts, because it can invent citations.

    No source, no rule

    The loader rejects any rule whose source ID isn't in sources/index.json.

    Why: test 3 holds by construction instead of by care.
    Cost: slower rule writing, which is fine for two cities.

    Vite + React + TypeScript (strict)

    One npm install && npm run dev. Versions pinned in package-lock.json, Node pinned with .nvmrc.

    Why: fastest path to a UI judges can run on a fresh laptop.
    Rejected: Next.js (we don't need its server), and plain HTML (UI state gets messy).

    Engine is a pure TS module

    The same code runs in the UI, in Vitest and in a CLI (npm run check irvine).

    Why: acceptance tests run without a browser, and coworkers can check a city from the terminal.

    No database: JSON in data/

    Sources, cities, rules and sample runs are files in git.

    Why: the data is small, diffable and reviewable in a PR, and coworkers read it on GitHub. If a database is ever needed, it is StrictDB.

    Claude in the app is optional

    One server-side route (a Vite middleware, so still one command), with the key from .env. Without a key, the UI uses the cached sample runs.

    Why: test 5 (fresh laptop, no key). The runtime model is picked at the paid-run gate with the claude-api skill, cheapest first.

    Letter from a template

    The draft is filled in from the flags and their citations. Copy is the only action.

    Why: the letter can only say what the flags say, and there is no send path (test 4).

    Sources saved by hand, once

    Each document is saved once, with its URL and checked date. No crawling, ever.

    Why: event rules, and Anaheim and leginfo return 403 to scripts. Statute text read on the california.public.law mirror is marked "mirror" until someone confirms it in a browser.

    Worktrees with separate paths

    Each parallel worker gets its own git worktree and owns separate folders, so their work never collides. I merge into local main after I review each diff.

    Why: merges without conflicts at speed. Cost: I am the review bottleneck, which is deliberate.
